# drawvid 架构说明

## 分层

`drawvid` 分为四层，层号越小越底层。上层可以依赖下层，下层绝不反向依赖上层：

1. **核心层 `drawvid.core`** —— 只有纯数据类型与异常（`Point`、`Rect`、`DrawvidError`、`CodecError`）。
   它是依赖图的**叶子**：不得 import 任何其他 `drawvid` 子模块。放这里的只有"谁都需要、且不依赖任何人"的东西。
2. **能力层 `drawvid.drawing` / `drawvid.video`** —— 两块互不相干的能力：
   前者把几何图形光栅化成路径并导出 SVG，后者把帧序列编码成字节流并支持时间轴。
   两者都只依赖 `core`，彼此**不互相 import**，因此可以各自独立演进与单测。
3. **集成层 `drawvid.pipeline`** —— 唯一允许同时看到画布与编码器的地方，负责把"画"和"编码"接起来。
   它依赖 `core`、`drawing`、`video`，是端到端脚本（`demo.py`）的入口。

这样划分的直接收益：任何一层的测试都不需要拉起整个系统。`video` 的编解码测试完全不需要画布，
`drawing` 的光栅化测试完全不需要编码器——它们只在 `pipeline` 的测试里第一次相遇。

## 依赖方向表

| 模块 | 可依赖 | 禁止依赖 | 理由 |
| --- | --- | --- | --- |
| `drawvid.core` | 无 | `drawing`、`video`、`pipeline` | 叶子层；被依赖者不得反向依赖依赖者，否则出现循环 import |
| `drawvid.drawing` | `core` | `video`、`pipeline` | 绘图不需要知道编码格式；知道就会把视频格式变更传导进绘图代码 |
| `drawvid.video` | `core` | `drawing`、`pipeline` | 编码器只处理"帧负载是字符串"，不关心它是怎么画出来的 |
| `drawvid.pipeline` | `core`、`drawing`、`video` | 无（最上层） | 集成层天然可以看见全部能力层 |

所有 import 一律用相对形式（`from .core import ...`），保证包被整体搬移时依赖关系不变。

## 被否决的方案

### (a) 用 ffmpeg 子进程封装编码器 —— 否决

最初考虑用 `subprocess` 调用 ffmpeg，把 SVG 帧序列交给它合成真正的 mp4。**否决**，原因有两条：

1. **引入外部进程依赖**。ffmpeg 不是标准库，也不保证在目标环境里存在或版本一致；一旦依赖它，
   项目就不再是可离线、可重复运行的，编码结果还会随本机 ffmpeg 版本漂移。
2. **编码器不可单测**。子进程的行为只能通过退出码与产物间接观察，无法在单元测试里构造边界输入
   （空序列、坏字节流）并断言异常类型；错误路径会退化成"看 stderr"。

因此 `ZipCodec` 采用**纯 Python 容器编码**：用 `io.BytesIO` + `zipfile` 把每帧写成
`frame_XXXX.svg`，再附一份 `manifest.txt` 记录 `fps` 与帧数。这一决策写进了 `ZipCodec.encode` 的
docstring，避免后来者重新引入子进程。代价是容器里存的是 SVG 文本而不是压缩视频，换来的是完全确定性、
零外部依赖、可对每个分支写断言。

### (b) 把绘图与视频合成一个模块 —— 否决

也曾考虑把所有代码放进单个 `drawvid.py`，理由是"文件少、import 方便"。**否决**，原因有两条：

1. **职责耦合**。几何光栅化与字节容器编码是两种完全不同的关注点，它们的变更原因、边界条件、
   测试方式都不一样；放在一起会让任一方的修改都可能破坏另一方。
2. **破坏分层**。合并之后"绘图依赖编码格式"就变得无法阻止，依赖方向表失效，反向依赖与循环
   import 也就无从检查。

维持 `drawing` 与 `video` 分离后，两者都只依赖 `core`，集成职责被集中到 `pipeline` 一层，
分层约束可以用一条"谁可以 import 谁"的规则机械地校验。
